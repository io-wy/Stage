## 0. 一句话总结

好的 RAG 系统，不是一次性搭出来的，而是靠 **知识 / 检索 / 生成 / 评测 / 反馈** 五个环节持续转起来的。

**核心心法**：答案错了先别急着改 prompt——先看是 **知识、召回、排序、截断还是生成** 哪一环的问题。RAG 的质量来自**闭环资产**，不是某一次 prompt 或模型替换。

**完整链路**：
`知识生产与治理 → Query 改写 → 多路检索 → Rerank 排序 → 证据截断 → 可信生成 → 自动评测 → 线上反馈回流`

工业级 RAG 的关键不是"把文档塞进向量库"，而是让知识持续更新、证据稳定召回、模型按证据回答、线上错误自动回流修复。

## 1. 简历 / 项目的「闭环」要求（原文出发点）

能打动面试官的 RAG 项目要有闭环：
**遇到什么问题**（如切块策略致上下文不连贯、步骤 AB 被拆分无法一起召回）
→ **采用什么优化策略**（如父子索引、查询重写）
→ **达到什么业务指标**（如加入父子索引后 recall 优化多少）。
而不是单纯堆技术炫技。

## 2. RAG 优化总览（8 模块）

| 模块 | 解决的问题 | 主要优化手段 |
|---|---|---|
| 知识工程 | 有没有正确知识 | 自动知识生产、语义切分、元数据补全、冲突治理 |
| Query 改写 | 用户问题能不能被搜到 | 主改写、子问题拆解、同义改写、改写模型微调 |
| 检索召回 | 能不能找回相关证据 | 向量检索、BM25、GraphRAG、标签加权、双路检索 |
| Rerank | 正确证据能不能排前 | 多路结果融合、去重、重排序模型 |
| 截断策略 | 关键证据会不会被丢掉 | 证据压缩、8K token 截断、保留高价值片段 |
| 可信生成 | 模型会不会胡编 | 证据约束 RL、安全奖励、URL 校验 |
| 过程评测 | 错误发生在哪一环 | 10 阶段评测、badcase 归因、中间产物保存 |
| 反馈闭环 | 线上错误能不能修复 | 点踩回流、分诊 Agent、知识草稿、评测集回归 |

## 3. 第一类：知识工程优化（底座 = 知识飞轮）

RAG 上限首先取决于知识库：库里没答案模型只能猜；知识过期输出过时答案；知识冲突即使检索到也可能答错。底座叫「知识飞轮」——知识可持续生产、清洗、更新、验证、回流。**知识可达率目标 95%+**。

- **3.2 自动化知识生产**：知识不只靠人工整理，从真实业务自动生产。操作寻路类 → 步骤型知识；API 参数类 → 模型可用知识；转人工 QA 类 → 客服高频问答沉淀。要点：知识库不是静态文档库，而是持续生长的系统。
- **3.3 Chunk 切分**：保留文档结构；避免太碎（语义不完整）/ 太长（召回不精准）。要点：chunk 不是越小越好也不是越大越好，**每个 chunk 保持相对完整的语义单元**。（原文：章节结构 + LLM 切分，长短片段合并调整）
- **3.4 元数据 Tag**：自动补标签，**直接参与检索和排序加权**（不是只为展示）。非审核类：行业、产品、人群；审核类：业务、行业、环节、地域。要点：显著提升检索精准度，适合企业 / 规则 / 产品知识库。
- **3.5 知识冲突治理**：冲突是事实问答错误的重要来源。常见冲突：政策变更 / 活动规则变化 / 旧文档未下线 / 历史文档仍被召回 / URL 失效。治理：无效 URL 识别、过时清理、冲突校验、历史过滤、错误停用。要点：**工业 RAG 里，知识冲突往往比模型能力更致命**。

## 4. 第二类：Query 改写优化

真实用户不按知识库标题提问（口语化、模糊、多意图、带上下文），直接拿原问题检索易失败。

- **多路动态改写**：主改写（补全语义、规范表达）/ 子查询改写（复杂问题拆子问题）/ 同义改写（扩大召回）。
- **改写模型微调**：基于线上日志 + 评测集约 **1.6 万条 SFT**，小模型 LoRA。效果：改写质量优秀率 **87.6%**、合格率 95%+。
- 要点：改写目标不是"改得更好看"，是**让问题更容易命中知识库**；它是明确、可评测、可训练的子任务，可用小模型承担。

## 5. 第三类：检索召回优化

- **5.1 混合检索**：工业 RAG 不能只押向量。多路并行：

  | 方式 | 适合场景 |
  |---|---|
  | 向量检索 | 语义相似问题 |
  | BM25 | 专有名词、字段、政策词、精确匹配 |
  | GraphRAG | 多跳关系、流程、规则依赖 |
  | 标签检索 | 行业、产品、业务场景过滤 |

  要点：**最稳的 RAG 通常是混合检索，而不是只靠 embedding**。

- **5.2 双路并行**：定向检索（按产品 / 行业 / 标签精准召回，优点准、风险漏）+ 通用检索（不强过滤、兜底覆盖，优点广、风险噪声多），再合并、去重、排序。要点：精准召回和泛化召回要同时存在。
- **5.3 GraphRAG**：不全量建图，只对**高频、高价值、高风险**知识建图（成本高）。适合多跳 / 流程 / 规则 / 实体关系 / 条件分支问题。

## 6. 第四类：Rerank 和截断优化

- **6.1 Rerank**：很多错误不是"没召回"而是排错。Rerank 把最有用的证据放到模型最容易看到的位置。
- **6.2 证据截断**：截断到 **8K tokens**，不是简单砍尾部，要保留：高相关 chunk / 关键规则 / 条件限制 / 操作步骤 / URL / 安全边界。要点：截断策略直接影响答案质量——**召回正确但截断错误，最终也答错**。

## 7. 第五类：可信生成优化

- **7.1 生成侧为何还错**：即使证据对，模型仍可能——不忠实用证据 / 自补不存在信息 / 编造 URL / 混合多片段致错 / 不符规范 / 触碰合规。→ 从 RAG 到**可信 RAG**。
- **7.2 证据约束 RL**：Qwen3-32B-RL + GRPO，奖励函数：Evidence Faithfulness（忠实证据）/ Style Compliance（符合规范）/ Safety（合规）/ URL Validity（链接真实）。要点：不能只用 prompt 要求"别胡说"，要把忠实性 / 安全性 / 链接有效性**写进训练和规则**。
- **7.3 URL 幻觉治理**：可信 URL = 来自证据，或命中 approved pool，且 HTTP 状态 200/301/302。效果：**URL 幻觉降 92.7%**。要点：高风险内容用**确定性规则兜底**，不靠模型自觉。

## 8. 第六类：过程评测优化

- **8.1 为何不只评最终答案**：答案错原因很多（改写错 / 路由错 / 没召回 / rerank 排错 / 截断丢证据 / 没按证据答 / 知识冲突）。只看答案只知"错了"，不知"怎么修"。
- **8.2 10 阶段评测**：链路拆 10 阶段（JUDGE / CLASSIFY / RERANK / BOUNDARY / REWRITE / RETRIEVAL / ANSWER / PREPARE / TRUNCATION / ROUTE），**每次评测保存中间产物**，改某环就从那环复跑（改 answer prompt → 从 answer 复跑；改截断 → 从 truncation 复跑；改 tag 权重 → 跑 retrieval/rerank 对比）。要点：分阶段评测把实验周期**从天级压到分钟级**。推荐开源框架 **DeepEval**（github.com/confident-ai/deepeval）。
- **8.3 Badcase 归因**（线上真实占比）：

  | 归因项 | 占比 |
  |---|---|
  | 知识冲突 | 45.8% |
  | 检索问题 | 32.4% |
  | LLM 问题 | 18.7% |
  | Reranker 问题 | 3.1% |

  要点：**错答不一定是 LLM 问题**——很多该修知识库 / 检索 / 排序，而非盲目改 prompt。先定位错误环节，再选修复手段。

## 9. 第七类：Agentic RAG 优化

普通 RAG 是固定检索 → 回答；**Agentic RAG 里模型不只是回答器，也是检索路径的决策者**（PLANNER 拆任务定路径，需要时再次检索，观察证据是否足够）。适合复杂 / 多跳 / 需工具调用问题。

- **路径级奖励**（Search-P1 核心）：不只奖励最终答案，也奖励中间路径。Path Reward（合理推理 / 检索路径）/ Soft Outcome Reward（答案错也给部分正确分）/ Format Reward（轨迹结构可解析）。
- 要点：关键是训练模型学会**正确地检索和推理**，不只看答案。

## 10. 第八类：线上反馈闭环

- **10.1 为何需要**：离线评测集永远覆盖不了全部线上问题。反馈来源：用户点踩 / 内部反馈 / AI 巡检 / 众测 / 客服反馈 / 群聊截图。
- **10.2 处理链路**：每一条线上错误都沉淀为下一次上线前的**回归测试**。
- **10.3 分诊 Agent**：只做粗分类，不直接判复杂根因。分类：知识缺失 / 回答有误 / 数据错误 / 分析偏差 / 产品需求 / 功能 Bug / 体验问题 / 无效反馈。真正根因分析交给后续。要点：**分诊 Agent 不要越权**——入口信息不完整，只适合粗分类。

## 11. 五阶段学习 / 落地路线（原文）

1. **基础 RAG**：chunk 切分、embedding、向量检索、BM25、rerank、prompt grounding → 能搭基础问答 RAG
2. **知识工程**：知识清洗、文档结构化、元数据 tag、冲突检测、更新机制 → 明白核心资产是知识库不是模型
3. **检索优化**：query rewrite、多路召回、混合检索、GraphRAG、rerank、截断 → 能定位修复"搜不到 / 搜错 / 排错"
4. **可信生成**：证据约束、引用校验、URL 校验、安全护栏、hallucination 评估 → 模型"按证据可靠地答"
5. **评测闭环**：分阶段评测、badcase 归因、自动评估员、反馈回流、回归测试集 → 系统持续迭代，不靠感觉调 prompt

## 附：对 Stage 外挂 RAG 的对照与启示（整理者加注，非原文）

> 以下是把文章框架映射到 Stage「案例 PDF 外挂知识库」场景的判断。Stage 方案细节见 memory `stage-rag-feasibility`。

**三点核心启示**：

1. **Agentic RAG 是 Stage 的天然主场**：文章把 agentic RAG 当高级优化，但 Stage 本身是 agent 编排引擎，戏子天生是检索路径决策者（拆任务 / 定路径 / 再检索）。普通 RAG 要专门搭 planner 才有，Stage 的戏子 + `rag_search` 工具开箱即有。是卖点不是补课。
2. **badcase 归因定投入重点**：知识冲突 45.8% + 检索 32.4% = 近 8 成错误在知识库质量 + 检索，不在 LLM / prompt。把解析 / 切分 / tag / 冲突治理做对，比调 prompt 重要得多。
3. **五阶段路线可直接当落地路线图**，与 Stage「最小闭环先行，质量后调」完全咬合。

**采纳节奏**（按 Stage 当前「无数据、先做骨架」阶段过筛）：

- **现在（骨架期）**：文章阶段一 + 二 → 最小闭环（入口 A 工具 + 弹性 ingestion + 结构切分 + tag）；**知识冲突治理**进设计（案例带版本 / 时效 metadata）。
- **有数据后**：阶段三 → 混合检索（向量 + BM25）+ rerank + query 改写。
- **飞轮转起来后**：阶段四五 → 评测闭环（badcase 归因）；**重武器（证据约束 RL / 改写微调 / GraphRAG 建图）按需**——当前无数据阶段属过度设计，不碰。
